# Дизайн: рабочее переключение контекста в планировщике noxis

**Дата:** 2026-08-23
**Статус:** одобрено пользователем (подход A — точечный фикс текущей схемы)
**Область:** `23-fixes/cpu/{task.c,interrupt.asm}`, `docs/scheduler-design.md`

## Проблема

Первое переключение в созданную задачу невозможно:

1. `task_create_prio()` (`task.c:111-113`) зануляет весь `registers_t` и
   заполняет только `.esp`/`.eip` → в кадре `.cs=0`, `.eflags=0`, `.ds=0`.
2. `scheduler_tick()` копирует структуру поверх живого кадра прерывания
   (`*r = tasks[next].regs`, `task.c:188`); стаб `irq_common_stub`
   (`interrupt.asm:52-54`) делает `iret` с CS=0 → #GP.
3. Кольцо 0→0 `iret` не загружает ESP из стека — задача не получает свой
   стек; синтетический iret-кадр на стеке задачи (`task.c:93-98`) никогда
   не потребляется.
4. Ротация никогда не выбирает слот 0 (`task.c:165` подменяет индекс), а
   ветка `next<0` (`task.c:176-181`) возобновляет SLEEPING-задачу — шелл
   голодает, `RUN blink` блокирует систему.

## Решение

### Инвариант

Каждый проход планировщика завершается одним из двух исходов:
- **без переключения** (выбрана текущая): флаг сброшен, стаб выходит
  обычным `iret` по нетронутому кадру;
- **с переключением** на задачу N: планировщик пишет 3 слова
  `[eip | cs | eflags]` из сохранённого контекста N по адресу
  `N->regs.esp - 12` (свободные слоты собственного мёртвого кадра N на
  её же стеке), кладёт этот адрес в `sched_resume_esp`, поднимает
  `sched_switch_pending`; эпилог стаба прыгает: `mov esp,[sched_resume_esp]`,
  и `iret` снимает eip/cs/eflags **со стека целевой задачи**, оставляя её
  ESP равным сохранённому.

### Изменения по файлам

**`cpu/interrupt.asm`** — только эпилог `irq_common_stub`:
```asm
    popa
    add esp, 8
    cmp byte [sched_switch_pending], 0
    jne .switch
    iret                       ; обычный выход: кадр не тронут
.switch:
    mov byte [sched_switch_pending], 0
    mov esp, [sched_resume_esp]
    iret                       ; снимаем eip|cs|eflags со стека целевой задачи
```
Плюс `[extern sched_switch_pending]`, `[extern sched_resume_esp]`.
`isr_common_stub` (исключения) не меняется — планировщик там не вызывается.
Флаг обязателен: через тот же эпилог выходят ВСЕ IRQ (клавиатура и др.);
безусловный прыжок стека отправлял бы их на чужой стек.

**`cpu/task.c`:**
- глобалы `volatile uint32_t sched_resume_esp; volatile uint8_t sched_switch_pending;`
- `task_create_prio()`: контекст новой задачи = нули +
  `.ds=0x10`, `.cs=KERNEL_CS`, `.eflags=0x202`, `.eip=task_trampoline`,
  `.esp=stack_top-16`; на стеке по адресу `.esp-12` записать стартовый блок
  `[trampoline | KERNEL_CS | 0x202]`. Синтетический iret-кадр удалить.
- `scheduler_tick()`:
  1. сохранить `cur->regs = *r`;
  2. взвешенное продолжение текущей (quantum_left) — как сейчас, но БЕЗ
     записи в `*r` (флаг остаётся сброшен);
  3. ротация по кругу **включая слот 0**, с пробуждением SLEEPING по
     `wake_tick`;
  4. если выбрана другая задача N: скопировать `*r = N->regs` (GPR/сегменты),
     записать блок `[N->regs.eip | cs | eflags]` по `N->regs.esp - 12`,
     `sched_resume_esp = N->regs.esp - 12`, `sched_switch_pending = 1`,
     `current_task = N`, `ticks++`, свежий quantum;
     если выбрана текущая — ничего не трогать;
  5. деградации «некого будить» больше нет: слот 0 всегда READY при живом
     шелле; страховочный случай (текущая спит, слот 0 не READY)
     невозможен и обрабатывается возобновлением текущей без флага.

**Документы:** `docs/scheduler-design.md` переписать под новую механику
(диаграмма, инвариант флага, убрать устаревшее «No stack recycling» —
стеки переиспользуются с `task.c:78-86`). README не меняется.

### Известные ограничения (приняты)

- Окно «флаг поднят до `iret`»: вложенное прерывание внутри эпилога может
  увидеть флаг; для учебного кольца-0 ядра принимается, документируется.
- Переполнение стека задачи не детектируется (как и прежде).
- `KILL` остаётся кооперативным; стеки переиспользуются по слотам.

## План тестирования (QEMU headless, монитор + VGA-буфер 0xb8000)

1. Регресс интерактива: загрузка → `HELP`, `ECHO hi`, `TIME` работают.
2. `RUN blink` → строка `[blink]` на row 20 появилась И шелл живой
   (следом `HELP` печатает список).
3. Параллельность: `RUN count` + `RUN clock` → обе строки обновляются,
   `TASKS` показывает двоих с растущими ticks.
4. Кооперативный kill: `KILL <id>` → строка задачи гасится, из TASKS исчезает.
5. Веса: `RUN spin` (w=3) против `RUN blink` (w=1) → соотношение ticks ≈3:1
   за ~10 секунд наблюдения.
6. `YIELD` из шелла возвращается с ответом «yielded», система живёт.

Критерий готовности: все 6 пунктов зелёные в headless-прогоне.
