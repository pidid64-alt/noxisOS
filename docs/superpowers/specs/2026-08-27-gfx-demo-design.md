# Спека: графическое демо для 25-osfs11 (TASK_GFX)

- **Дата:** 2026-08-27
- **Статус:** утверждено пользователем (скоуп, контент, точка входа, архитектура A)
- **Проект:** `25-osfs11` (Orange'S, 32-бит, микроядро с передачей сообщений)

## Цель

Первый шаг к графическому окружению: доказать пиксельный пайплайн — переключение
VGA в графический режим, драйвер-фреймбуфер, примитивы рисования и стабильный цикл
анимации. Окна, мышь и VESA — вне скоупа этого этапа.

## Утверждённые решения

| Вопрос | Решение |
|---|---|
| Скоуп | Демо: фреймбуфер + рисование |
| Контент | Тестовые паттерны + анимация (прыгающий мячик) |
| Точка входа | Команда `demo` из шелла, ESC возвращает текстовую консоль |
| Архитектура | Вариант A: выделенный таск `TASK_GFX` + syscall-клиент (не вписывать в TTY) |

## Архитектура

Новый kernel-таск **`TASK_GFX`** (ring 1, `PRIVILEGE_TASK`, как TTY/SYS/HD/FS/MM)
с собственным стеком; живёт бесконечным циклом `send_recv(RECEIVE, ANY)` → обработка
сообщения. Юзер-процесс `demo` (обычная команда из ФС, как `echo`/`pwd`) вызывает
syscall-враппер `gfx_run()`, который через `send_recv(BOTH, TASK_GFX, &msg)`
усыпляет процесс до ответа таска после завершения демо.

Обоснование против варианта B (вписать в `task_tty`): TTY обрабатывает все консоли
и клавиатуру — анимационный цикл блокировал бы ввод; смешение ответственностей;
при развитии в оконный сервер всё равно потребовалось бы выделять отдельный таск.

## Компоненты

- **`kernel/gfx.c`** — таск `task_gfx`:
  - цикл сообщений;
  - переключение VGA **портами, без BIOS** (в PM BIOS недоступен): таблицы
    регистров mode 13h и text mode 3 — misc `0x3C2`, sequencer `0x3C4`,
    CRTC `0x3D4`, graphics controller `0x3CE`, attribute controller `0x3C0`;
  - фреймбуфер `0xA0000`, 320x200, 1 байт/пиксель (линейный, mode 13h);
  - примитивы: `putpixel`, горизонтальные/вертикальные линии, заливка
    прямоугольника, окружность (алгоритм midpoint);
  - рендер в **двойной буфер 64 КБ** (BSS таска) → `memcpy` в `0xA0000`
    (без разрывов кадра);
  - фазы демо: тестовые паттерны (~2 с: цветовые полосы, градиент, фигуры) →
    анимация прыгающего мячика;
  - темп кадров по тикам `TASK_SYS` (`GET_TICKS`), 1 тик = кадр (~18 FPS).
- **`command/demo.c`** — клиент: вызывает `gfx_run()`, после возврата печатает
  `[demo finished]`. Добавляется в `BIN` командного Makefile — попадает в tar и
  на диск через существующий конвейер `make install-cmdtar`.
- **`lib/gfx.c`** + строка в **`lib/syscall.asm`** — враппер syscall (паттерн
  `get_ticks`).
- **Точечные правки существующих файлов:**
  - `kernel/global.c` — запись в `task_table`;
  - `include/sys/const.h` — `STACK_SIZE_GFX`, номер syscall, типы сообщений
    `GFX_RUN` и `TTY_POLL_KEY`, `NR_TASKS` + 1;
  - `include/sys/proto.h` — объявления;
  - корневой `Makefile` — `kernel/gfx.o` в `OBJS`, `lib/gfx.o` в `LOBJS`;
  - `kernel/tty.c` — один новый case `TTY_POLL_KEY`: неблокирующее извлечение
    одной клавиши из буфера консоли процесса-отправителя GFX_RUN (tty
    определяется по источнику сообщения; для выхода по ESC; клавиатура
    остаётся в собственности TTY).

## Поток данных (один запуск)

```
shell: $ demo
  → exec загружает demo из ФС
  → demo: syscall gfx_run() → MSG{GFX_RUN} в очередь TASK_GFX, процесс спит
  → TASK_GFX: переключение в mode 13h
      цикл кадров:
        рисование в двойной буфер
        memcpy буфера → 0xA0000
        опрос TTY (TTY_POLL_KEY) на ESC
        темп: 1 тик TASK_SYS = 1 кадр
      паттерны ~2 с → анимация мячика
  → ESC или конец фаз
  → переключение в text mode 3
  → ответ GFX_DONE
  → demo печатает [demo finished] и выходит в шелл
```

## Ошибки и устойчивость

- Повторный `demo` во время работы демо встаёт в очередь сообщений таска и
  обслуживается после первого (штатная очередь книжного ядра).
- Переключение режима — детерминированные записи регистров; пути отказа нет
  (поведение VGA/QEMU одинаково и известно).
- Выход по ESC — основной путь; fallback при проблемах с `TTY_POLL_KEY`:
  фиксированная длительность демо (~10 с) с автопоказом. Решение фиксируется
  на этапе реализации.

## Тестирование

1. **Headless QEMU** (без дисплея, через monitor-сокет):
   - в графическом режиме `pmemsave 0xA0000 64000 <file>` — два снапшота в
     разные моменты;
   - проверка (а): индексы пикселей первого снапшота соответствуют ожидаемым
     паттернам (стандартная палитра mode 13h известна → конвертация в PNG);
   - проверка (б): снапшоты различаются → анимация движется.
2. **Ручной прогон** в пользовательской ВМ: `demo` → паттерны, анимация,
   ESC → возврат консоли; повторный запуск; консоль работает после выхода.

## Предпосылки из сессии 2026-08-27

- Конвейер доставки команд на диск работает: `make install-cmdtar` →
  `command/install` → tar с `kernel.bin, echo, pwd, hdldr.bin` → dd в
  `100m.img` по смещению `(ROOT_BASE + INSTALL_START_SECT)` → `untar()`
  при загрузке. `demo` доедет этим же путём.
- Зафиксирован осиротевший tar 2008 года по абсолютному смещению `0x17000`
  (артефакт старой раскладки; ФС читает по `0x26000`). Регион можно не
  трогать; при желании — будущая чистка.
- Фикс ассертов в `msg_receive` (`kernel/proc.c`, перенос до `block()`) —
  в дереве; падение `assert(p_who_wanna_recv->p_msg != 0)` на ln481
  относится к старому бинарнику.
